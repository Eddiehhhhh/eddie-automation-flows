# Tencent complex-sheet capture candidate

This candidate prepares data locally; it does not enable a schedule, update the private repository, or release another task's integration lock. The public automation repository must never contain source text, generated captures, signed export URLs, credentials, or CI artifacts containing them.

## Capture and review

- Run `scripts/capture_tencent_complex.py --output-dir <new-private-staging-directory>` with `TENCENT_COMPLEX_FILE_ID` and the existing Tencent credential available to the runtime. `--previous-dir <verified-prior-version>` skips an unchanged capture only after validating every prior entry and freshly exporting and comparing every new Excel entry; unchanged record metadata alone is insufficient to detect image changes. The process exits without publishing on missing or inconsistent source data. When a verified previous version exists, missing previously observed sheets, populated cells, fields, views, or records cause a stop rather than silent deletion; an intentional source deletion requires separate reconciliation.
- The private capture contains `snapshot.json`, `阅读入口.md`, `excel-manifest.json`, and `excel/` OOXML entries. The manifest records the original export's size and SHA-256, plus a SHA-256 for each extracted entry. Entry readback is checked before staging. `scripts/rebuild_tencent_excel.py --capture-dir <verified-version> --output <new-local-xlsx>` rebuilds the Excel container and independently verifies all entry hashes. Repacking the entries is not guaranteed to reproduce the source XLSX bytes.
- Both regular and smart sheets, including hidden sheets, are represented. Cell API responses with and without formula mode are kept separately. For each regular sheet, every coordinate in the provider-declared grid must either be explicitly returned by the default response or be a non-anchor interior of a valid, non-overlapping merged range; populated coordinates must also appear in formula mode. Missing coordinates fail closed, including on the first capture. This proves coverage relative to the provider-reported grid and merged ranges; the API does not provide an independent completeness total. Image references remain in structured data; downloaded Excel image files are supplementary. Record-level image-to-file identity remains unverified. Excel export can differ from source text and may not preserve hidden state; do not replace the structured snapshot with it.
- Temporary signature parameters are removed from image URLs; ordinary width/height parameters are retained. A source or extracted XML containing a detected credential-bearing query is rejected. This is a narrow check, not a general secret scanner.

## Private staging and publication gate

`scripts/stage_tencent_complex.py --capture-dir <capture> --vault <private-checkout> --relative-destination <Raw/06 TencentDocs/subdirectory> --expected-index <absent-or-sha256>` stages only the declared files in an immutable version and creates a managed `索引.md`. It validates entry hashes before and after copy, rejects a changed index, keeps old versions, and does not run Git. A failed index write can leave a complete unreferenced version; a retry with the same expected index reuses it after validation.

For any eventual GitHub Actions integration, perform the applicable project preflight and acquire the authorized integration ownership before touching private main. Preserve the `eddie-private-vault-writers` concurrency group; check the current private head and exact prior index hash, use the existing scoped private-vault publisher with non-force ancestry checks, and read back the index, snapshot, manifest, and every expected object. Do not run publication if the vault integration lock belongs to another task. Cloud execution must not be claimed operational until a real private run and natural schedule have been independently read back.

## Isolated cloud proof candidate

`.github/workflows/tencent-complex-proof.yml` is a manual-only candidate. It uses the existing `eddie-private-vault-writers` concurrency group and the existing private-vault/Tencent credentials. It emits no private payload or artifact into the public automation repository. Its proof driver accepts only `codex/tencent-proof-<10-20 digits>` in the private repository, never `main`; verifies private repository identity, fetches main and checks ancestry, rejects a dirty checkout or unrelated branch delta, scopes staged paths to `Raw/06 TencentDocs/云端验证`, validates every staged Git blob, invokes the existing non-force private publisher, and performs a fresh independent private clone/object hash readback. The target proof branch must already exist and contain `.sync/tencent-complex/test-binding.json` with the source file ID. That binding is private and is never part of the public code.

Before preparing the proof branch or dispatching this workflow, the responsible operator must satisfy the actual vault integration-lock rules. Do not dispatch while another task owns the integration lock; a GitHub concurrency group is not a substitute. The candidate workflow is not yet registered on the default automation branch, and no private binding, test branch, workflow dispatch, or cloud publication has been made by this change. After a permitted run, verify external results independently; local tests do not prove cloud operation.

A proof may fail after the remote test branch was already updated. Keep its numeric nonce and inspect that exact branch and its manifest before any retry; do not create a replacement proof blindly. For an unchanged source and Excel, the proof makes no commit and independently re-clones and verifies the prior proof objects and current proof-branch head before reporting success. The proof branch and binding are prerequisites; the implementation deliberately does not create either or release a vault lock.
